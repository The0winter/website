# 论坛推荐算法

2026-10-03 实现 `balanced-v1`。论坛分页接口 `GET /api/forum/posts?view=answers&format=page&tab=recommend&limit=20` 使用本算法；旧数组接口和书籍讨论列表保留完整内容查询语义。推荐单位是单篇回答或独立文章，文章评论不进入推荐。

## 排序与探索

从近期内容、基础质量、轮换分桶、近期热度和个人兴趣五路召回，合并后最多约 840 条候选，再生成最多 240 条的会话列表。召回查询只读取排序特征，展示摘要按实际交付页读取，正文仍从原内容接口读取。排序复用主题相似度和窗口计数，避免重复构造集合；优化前后在 840 条候选、12 种组合下逐条核对顺序和推荐理由一致。

- 默认槽位倾向为兴趣 50%、热点 25%、相邻兴趣 15%、低曝光内容 10%。这是候选充足时的初始策略，不是强制填满的承诺；通道无合适内容时按质量和多样性补位。
- 兴趣使用书架、最近阅读、有效论坛阅读、赞同和主动关注。短期与长期信号分别按 7 天和 45 天半衰期衰减，单个维度饱和，评论不自动视为喜欢。
- 热度只使用上线后的真实互动，同一身份、内容和自然日去重。有效阅读权重 1、赞同 3、评论 0.5；游客权重乘 0.35。热度含 24 小时和 7 天衰减项，历史导入的赞同、浏览总数不伪装成新热度。
- 初始质量是长度、来源等轻量启发式，配合平滑后的阅读/赞同比率；不把它称为内容事实质量或人工审核结果。主题使用类别、标签与正文关键词；通用“读后感”“含剧透”标签不作为主题。
- 收录内容按“来源站点 + 原作者”区分作者，不按同一个上传账号挤占作者配额。新鲜度使用原文发布时间，不用批量导入时间冒充新文章。

## 防止重复与过度集中

推荐流已有效阅读的内容冷却 30 天；实际曝光的内容冷却 24 小时，同一周已有两个不同日期曝光也暂不再推。预加载、仅获取列表和打开链接不计为有效阅读。

会话内排除完全重复正文，并对同一本书、长度接近的长文做严格阈值 SimHash 近重复检查。任意连续 20 条最多一篇同问题回答；同书和同作者各尽量不超过两条，同主题尽量不超过十条且不连续超过两条，另有主题相似度惩罚。供给不足时可放宽作者、书籍和主题配额；权限、屏蔽、正文去重、同问题间隔和推荐冷却不放宽。热门与关注允许重访已读内容，仍遵守权限、显式屏蔽及列表多样性。

分页会话保存顺序 6 小时，签名游标绑定身份、标签、位置及最近 19 个已交付条目。翻页、失败重试和阅读返回不重新洗牌。每页重新检查当前书籍权限、收录状态及用户屏蔽；过期游标自动尝试新建一次会话，内容去重后追加，保留已有卡片和阅读位置。续接失败保留原列表并提供重试，不循环创建会话。

## 用户控制与行为记录

2026-10-03 按读者使用方式调整：首页移除“推荐偏好”“换一批”及其整行占位，移动端答案紧接分类栏，桌面恢复原有 24px 间距。滑动预览同步调整；推荐自动生成，无需读者先选策略。卡片菜单仍支持屏蔽书籍/主题/作者、减少相似内容、关注书籍/作者及撤销。关注页只展示真实关注范围。

服务端保留已有的个性化开关、探索比例和学习重置语义，不因移除入口覆盖用户已经保存的选择。关闭后仍提供多样化公共内容并保留显式屏蔽；重置以时间边界忽略旧兴趣信号，仍保留去重冷却和手动偏好。

登录用户的偏好保存在服务端，可跨设备同步；游客使用 HttpOnly 的本站随机 cookie，服务端仅保存 HMAC 身份。旧本地屏蔽分批迁移。偏好和阅读凭据等待登录状态确认后获取；身份切换时取消旧请求、清空内存缓存，过期响应不能写入新身份。各身份的游标、行为凭据和偏好删除操作互相隔离，取消关注也作用于已有关注分页。

卡片达到 50% 可见并停留约 1.1 秒才报曝光；正文仅累计前台、当前可见回答的阅读时间，弹层和后台页面不计时。有效阅读门槛按内容长度为 12–45 秒，并要求至少 10% 阅读位置。服务器签发凭据并验证时间、身份、内容权限，不能将前端任意 entry ID 作为有效行为。此机制抑制误计数，并不声称可以识别所有脚本伪造。行为失败不会中断浏览或业务写入。

## 运维与验证

新增 `ForumRecommendation*` 集合均为派生索引、偏好、会话或行为数据；不改写原帖、回答和书籍。事件保留 90 天，会话 6 小时，无新增互动的热度记录 30 天后过期。索引任务每分钟按 `updatedAt + _id` 检查点有界增量处理，每 6 小时重新扫描继承的书籍/问题特征；返回内容时另做实时可见性校验。部署先在新版本目录构建并预热派生索引，再使用既有兼容发布/回滚流程切换。

关键实现：`server/services/forum-recommendation-{ranking,catalog}.js`、`forum-recommendations.js`、`server/routes/forum-recommendations.js`；客户端行为记录位于 `web-next/lib/forum-activity.ts`。

已覆盖 SQLite 和原生 MongoDB 的身份隔离、权限变化、冷却、去重、稳定分页与事件验证，以及 320/390/1440px 浏览器交互、跨设备偏好、曝光计数和原有论坛性能/收录回归。相关测试为 `server/tests/forum-recommendations.test.js` 和 `web-next/tests/forum-recommendations.spec.ts`。浏览器测试按项目约定在首次导航前隔离 GA；生产验收额外屏蔽推荐行为上报和阅读计数。

后续调参应同时看有效阅读率、负反馈率、7 天重复曝光率、不同书籍/作者/主题覆盖及留存，区分新老用户、供给量和入口。初始比例、阈值与主题分类仍需真实数据验证；本版没有伪造 A/B 结果，也没有在数据不足时引入协同过滤、在线 bandit 或自动训练模型。

## 加载速度调查与待实施方案（2026-10-03）

本节是后续性能方案；本次实际代码修改仅包含上述首页简化和过期分页自动续接。以下基线来自线上 `957b99b`，没有将本次界面调整描述为已完成提速。

### 实测结果

隐藏浏览器、新游客、首次直接访问论坛，导航前屏蔽 GA、推荐行为及阅读计数。390px 与 1440px 各取一次完整网络时间线；这是单次诊断，不是总体平均值或 p95，也未模拟国内移动网络。

| 项目 | 手机 390px | 桌面 1440px |
| --- | ---: | ---: |
| 导航至首条卡片可见 | 5.83s | 6.12s |
| HTML 首字节 | 0.84s | 0.84s |
| 导航至身份请求开始 | 2.28s | 2.57s |
| 身份请求 | 0.28s | 0.28s |
| 偏好请求 | 0.48s | 0.49s |
| 首屏推荐接口 | 2.43s（5条） | 2.56s（20条） |

手机时间线：身份约在 2.28s 开始，偏好在 2.56s 开始，推荐直到 3.04s 才开始；第二页接口另需约 1.51s。页面初始化和客户端串行请求也占据明显时间，不能只优化排序函数。

后端只读诊断另使用独立进程：数据库 ping 为 198–207ms，代表性最新/质量/发现召回的数据库执行时间仅 0–5ms，均使用索引。5 条展示仍召回约 435–451 条候选、排序最多 240 条；模拟完整读取链为 3.10–4.24s，排序 180–264ms，展示内容及当前权限核对约 630ms，包含 14 次 find。这些结果含独立连接池的冷启动，且不包含真实接口的所有写入及序列化，不与浏览器接口时间混作同一指标。样本中未发生内容索引过期修复。

主要原因是共享候选反复读取，以及多组依赖查询逐轮等待远程数据库。手机 `limit=5` 只限制末端展示，不能减少前面的整批准备；单纯调小返回数量或增加索引并不能解决当前主要耗时。

### 建议实施顺序

1. **共享候选与热点提前准备。** 常驻 API 进程维护有容量上限的候选特征、热点和派生展示缓存，初始刷新间隔 30–60 秒；同一批并发请求共用一次刷新。保留轮换分桶和每次排序种子，不缓存一份所有人都相同的最终列表。当前规模先使用进程内缓存，多实例确有需求时再引入共享缓存。缓存不包含用户身份、行为凭据、偏好、阅读排除或最终个性化响应；实际交付仍验证当前权限和屏蔽。缓存带算法/目录版本、有限过期回退和失效机制。依据：[MongoDB 预计算数据模式](https://www.mongodb.com/docs/manual/data-modeling/design-patterns/computed-values/computed-schema-pattern/)。

2. **合并必须实时执行的数据库查询。** 将交付内容的“推荐条目 → 帖子/回复 → 书籍”三轮读取改为一次有界 MongoDB 聚合，保留现有其他数据库兼容路径。权限仍实时判断，重新核对书籍私密/删除、回答归属、收录/重复状态和内容版本。把内容变化与浏览数、赞同数变化分开，避免仅计数更新就同步重建正文特征。以执行计划和阶段耗时判断效果，不能只看查询总次数。依据：[MongoDB 查询计划解释](https://www.mongodb.com/docs/manual/tutorial/analyze-query-plan/)。

3. **缩短首屏初始化。** 将身份初始化、推荐偏好和首屏数据设计为一次受控初始化响应，服务端根据现有 Cookie 校验身份，并由同一个入口建立游客身份；可并行的服务端读取提前开始。客户端得到结果后一次初始化各缓存，不再依次发三个请求。旧偏好迁移必须先完成，登录/退出时仍取消旧请求，不能通过直接同时发起现有接口引入游客身份竞争。站内进入论坛可在身份确认后按导航意图预取，限制重复和无用请求；直接访问再评估服务端首屏数据注入与流式渲染，以消除等待客户端脚本后才取数的问题。依据：[Next.js 数据获取](https://nextjs.org/docs/app/getting-started/fetching-data)。

4. **逐步排序并保持会话稳定。** 在前面取数优化后，再将首次排序改为 40–80 条，后续沿相同候选快照、种子、偏好版本和阅读排除继续生成。只读样本中排序 40 条为 40–59ms，前缀与原 240 条一致；收益为数百毫秒以内，不能替代前面的数据库优化。延伸时保留已展示顺序、同问题间隔和跨页去重，不通过裁短列表造成内容提前耗尽。活跃用户的兴趣汇总可随后做有界缓存，并随屏蔽、重置和有效阅读失效。

常驻 API 启动时预热必要连接及缓存，再进入就绪状态。部署脚本的独立 Node 进程预热不会将连接池带入常驻服务；不能把诊断冷进程的连接排队当作每次线上请求都存在的问题。完成应用改进后如仍受约 200ms 数据库往返限制，再核对服务与数据库的部署区域及迁移成本，不仅凭 RTT 推断地理位置或贸然迁库。连接依据：[MongoDB Node 连接池](https://www.mongodb.com/docs/drivers/node/current/connect/connection-options/connection-pools/)。

### 验收口径

先增加无身份明文的阶段计时，分开记录连接等待、数据库、排序、权限校验与首卡可见；覆盖冷/暖缓存、游客/登录、5/20 条、翻页及适度并发。第一阶段建议目标为相同测点的暖请求首屏接口 p50 ≤ 1.2s、p95 ≤ 2s，登录用户 p95 暂定 ≤ 2.5s；这些是待验证目标，浏览器完整首屏另计，不能用接口时间替代。

推荐质量约束保持：不混用身份，不展示已私密/移除内容，不绕过显式屏蔽、阅读与曝光冷却；翻页重试和阅读返回稳定，缓存刷新不改变已展示顺序。前端保留现有先 5 条、空闲预载到 10 条的策略；骨架仅用来交代等待，不作为实际提速指标。

本次首页调整通过 320/390/1440px 布局验收和 13 项浏览器回归，包含自动续接失败后的重试、已有内容去重保留、返回位置、卡片反馈撤销、关注跨设备及身份切换。原始诊断、执行日志和截图保存在本地 `.runtime/task-artifacts/forum-home-speed-20261003/`，不提交用户数据或运行产物。
